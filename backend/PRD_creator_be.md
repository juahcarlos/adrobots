# Техническое задание: автоматическое создание кампаний в Keitaro

## 1. Цель проекта

Разработать небольшое веб-приложение для автоматического создания рекламных кампаний в Keitaro.

Пользователь заполняет три поля, нажимает кнопку, после чего приложение самостоятельно создаёт кампанию, настраивает её параметры и добавляет два потока с необходимой логикой перенаправления посетителей.

Пользователю не нужно самостоятельно заходить в Keitaro и настраивать кампанию вручную.

## 2. Интерфейс

Главная страница содержит форму из трёх полей:

### 2.1. Name — название кампании

Текстовое поле. Из названия формируется alias кампании (под капотом).
- `alias` — URL-идентификатор: `name`, в котором `_` заменены на `-` (`my_campaign_1` → `my-campaign-1`);

### 2.2. Geo — страна

Поле выбора страны. Первая пустая опция показывает `MX,AU,RO,...`.

Для передачи в Keitaro используется двухбуквенный код страны по стандарту ISO 3166-1 alpha-2.

Примеры:
- Germany — DE
- United States — US
- Russia — RU

Список стран берётся из пакета `pycountry` (ISO 3166-1 alpha-2). Бэкенд отдаёт фронту список кодов через эндпойнт, фронт выводит их в виде select. Код, которого нет в списке, при создании отклоняется.

Пользователь выбирает страну из списка, а приложение передаёт её код в API.

### 2.3. Offer — оффер

Поле с подсказками: пользователь вводит ID или часть названия, ниже показывается список подходящих офферов Keitaro (до 20), выбранный оффер подставляется в поле.

При открытии страницы приложение получает список офферов через наш бэкенд (`GET /offers`), который запрашивает их у Keitaro.

Пользователь выбирает нужный оффер. В запросах используется его ID.

### 2.4. Кнопка создания

Кнопка `Create`.

После нажатия запускается последовательность создания кампании.

На время выполнения кнопка блокируется и показывает «Создаём...», чтобы пользователь не мог случайно запустить несколько одинаковых операций.

## 3. Настройки подключения

Данные для подключения к Keitaro не должны вводиться пользователем при каждом создании кампании.

В конфигурации приложения хранятся:

- URL Keitaro API;
- API Token;
- URL подключения к БД (DATABASE_URL);
- ID группы кампаний (GROUP_ID=10332, FORTESTS).

API Token хранится в конфигурации серверной части приложения и не передаётся браузеру. Все запросы к Keitaro API выполняются сервером.

Домен и источник трафика определяются через API Keitaro при создании кампании. Группа кампаний задаётся в конфигурации приложения. Домен (GET /domains) берётся из списка, если в нём ровно один элемент, иначе ошибка. Источник (GET /traffic_sources): если список пуст, `traffic_source_id` равен 0, иначе берётся первый элемент.

## 4. Логика создания кампании

После отправки формы приложение выполняет следующие действия.

### Шаг 1. Проверка данных

Проверить:
- заполнено ли название;
- соответствует ли название формату `test_фамилия_...`;
- выбрана ли страна;
- выбран ли оффер;
- доступны ли необходимые настройки подключения.

Если данные некорректны, показать пользователю понятную ошибку и не отправлять запросы на создание.

### Шаг 2. Подготовка данных кампании

Подготовить объект кампании для Keitaro.

Использовать:
- `name` — название из формы;
- `alias` — URL-идентификатор: `name`, в котором `_` заменены на `-` (`test_semyonoff_campain875` → `test-semyonoff-campain875`);
- `domain_id` — ID домена из `GET /domains`;
- `group_id` — ID настроенной группы;
- `traffic_source_id` — ID источника из `GET /traffic_sources`, 0 если список пуст.

Обязательные поля `POST /campaigns`: `alias`, `name`.

### Шаг 3. Локальная запись

После проверки и подготовки данных, до запросов в Keitaro, в локальную БД одной транзакцией записываются:

- кампания (Campaign) со статусом `pending`, страна сохраняется в `Campaign.geo`;
- два потока (Stream): Google GEO и Selected Offer;
- оффер (Offer) и его привязка к потоку 2 (StreamOffer: `share` 100, `status` active, оба флага false). Поток 1 сохраняется без привязок офферов.

`keitaro_id` кампании и потоков на этом этапе NULL. Offer создаётся, если записи с таким `keitaro_id` нет, иначе используется существующая. `name` и `preview_path` берутся из `GET /offers`.

#### Модели БД

Campaign:
- `id` — внутренний ID;
- `keitaro_id` — ID кампании в Keitaro, уникальный, NULL допустим (пока кампания не создана в Keitaro или после отката);
- `name`, `alias`;
- `domain_id`, `group_id`, `traffic_source_id`;
- `status` — `pending`, `synced` или `failed`;
- `last_error` — текст ошибки при `failed`, иначе NULL;
- `geo` — код страны, varchar(8), NULL допустим;
- `created_at`.

Stream:
- `id` — внутренний ID;
- `keitaro_id` — ID потока в Keitaro, уникальный, NULL допустим;
- `campaign_id` — ссылка на Campaign;
- `name`, `type`, `schema`, `action_type`, `position`;
- `filters` — имена фильтров потока через запятую, пусто если их нет (добавлено для редактора);
- `clicks_today` — клики за сегодня, обновляются при Fetch (добавлено для редактора).

Offer:
- `id` — внутренний ID;
- `keitaro_id` — ID оффера в Keitaro, уникальный;
- `name`;
- `preview_path` — для ссылки preview в редакторе.

StreamOffer (привязка оффера к потоку):
- `id` — внутренний ID;
- `stream_id` — ссылка на Stream;
- `offer_id` — ссылка на Offer;
- `share` — вес, целое;
- `pinned` — вес закреплён, по умолчанию false;
- `status` — `active` или `removed`;
- `is_unpublished` — привязка не опубликована в Keitaro;
- `is_deleted_unpublished` — удалена локально, удаление не опубликовано;
- уникальность пары (`stream_id`, `offer_id`).

### Шаг 4. Создание кампании в Keitaro

Выполнить `POST /campaigns` с данными, подготовленными на шаге 2 (`domain_id` и `traffic_source_id` числами, `group_id` строкой).

В ответе получить ID созданной кампании, он нужен для создания потоков. Сразу сохранить его в `keitaro_id` локальной записи кампании отдельным коммитом.

Если Keitaro вернул ошибку, прекратить выполнение, выполнить откат (шаг 6) и вернуть ошибку клиенту.

### Шаг 5. Создание потоков

После создания кампании создать два потока через `POST /streams`.

**Обязательные поля каждого потока:**
- `campaign_id` — ID созданной кампании.
- `type` — тип потока.
- `name` — название потока.
- `action_type`: `http`.
- `schema` — схема потока, задаётся отдельно у каждого потока.

**Поток 1 — Google:**
- `name`: `Google GEO`
- `position`: `1`
- `type`: `forced`
- `schema`: `redirect`
- `filters` — массив с GEO-фильтром:
  - `name`: `country`
  - `mode`: `accept`
  - `payload`: массив с ISO-кодом выбранной страны.
- `action_type`: `http`
- `action_options`: `{"url": "https://www.google.com"}`
- `state`: `active`
- `collect_clicks`: `true`

**Поток 2 — выбранный оффер:**
- `name`: `Selected Offer`
- `position`: `2`
- `type`: `default`
- `schema`: `landings`
- `offers` — массив с одним элементом:
  - `offer_id` — ID выбранного оффера из `GET /offers`.
  - `share`: `100`
  - `state`: `active`
- `action_type`: `http`
- `state`: `active`
- `collect_clicks`: `true`

### Шаг 6. Завершение и откат

После каждого успешного шага Keitaro (кампания, поток Google GEO, поток оффера) внешний ID сразу сохраняется в локальную запись отдельным коммитом.

Если все шаги успешны, статус кампании становится `synced`.

При сбое на любом шаге:

- в Keitaro удаляется всё созданное, в обратном порядке: поток оффера, поток Google, кампания. Ошибки удаления только логируются и не подменяют исходную ошибку;
- кампания получает статус `failed`, текст ошибки пишется в `last_error`;
- если удаление в Keitaro прошло без ошибок, `keitaro_id` кампании и потоков обнуляется; если удаление упало, внешние ID остаются в БД для ручной очистки;
- клиент получает ошибку, форму можно отправить заново. Записи `failed` остаются в БД.

Кампании, подтянутые из Keitaro редактором (Fetch), сохраняются со статусом `synced`.

## 5. Работа с API Keitaro

Для реализации используются следующие API-методы.

#### Получение справочников

При загрузке формы:
- `GET /offers` — получение списка офферов и их ID для выбора пользователем.

При создании кампании (шаг 2):
- `GET /domains` — список доменов;
- `GET /traffic_sources` — список источников трафика.

Справочники `/stream_filters`, `/stream_schemas`, `/streams_actions`, `/stream_types` не запрашиваются, значения заданы в разделе 4. Допустимые значения `type` в `POST /streams`: `forced`, `regular`, `default`.

#### Создание объектов

- `POST /campaigns` — создание кампании;
- `POST /streams` — создание потока Google;
- `POST /streams` — создание потока выбранного оффера.

При откате (шаг 6) созданные потоки и кампания удаляются через соответствующие методы удаления Keitaro API.

Все запросы выполняются с авторизацией через API Token. Заголовок авторизации: `Api-Key`. Названия методов приведены без базового URL API.

Запросы к Keitaro идут с таймаутом. Таймаут или недоступность Keitaro возвращается как ошибка текущего шага. POST-запросы автоматически не повторяются, иначе будет дубль кампании.

## 6. Последовательность работы приложения

Общий сценарий:

1. Пользователь открывает страницу.
2. Приложение запрашивает у нашего бэкенда список стран (`GET /countries`) и список офферов (`GET /offers`).
3. Пользователь вводит название кампании.
4. Выбирает GEO.
5. Выбирает оффер.
6. Нажимает Create.
7. Приложение проверяет введённые данные и настройки подключения.
8. Записывает в БД кампанию со статусом `pending`, два потока и привязку оффера.
9. Создаёт кампанию через POST /campaigns и сохраняет её ID.
10. Создаёт поток с GEO-фильтром и перенаправлением на Google, сохраняет его ID.
11. Создаёт поток с выбранным оффером, сохраняет его ID.
12. При успехе ставит статус `synced`, при сбое удаляет созданное в Keitaro и ставит `failed`.
13. Показывает результат выполнения.

## 7. Обработка ошибок

Приложение должно корректно обрабатывать ошибки на каждом этапе.

Примеры:
- ошибка авторизации в Keitaro;
- недоступность API;
- ошибка сохранения в БД;
- некорректные параметры кампании;
- отсутствие выбранного домена или группы;
- ошибка создания кампании;
- ошибка создания первого или второго потока.

Пользователь должен видеть, на каком именно этапе произошла ошибка.

Если кампания уже создана, но создание одного из потоков завершилось ошибкой, нельзя сообщать об успешном завершении всей операции: созданное в Keitaro откатывается (шаг 6), кампания в БД получает статус `failed`. Если откат в Keitaro не удался, внешние ID остаются в БД, чтобы объекты можно было найти и удалить вручную.

## 8. Результат работы

После успешного выполнения в Keitaro должна появиться новая кампания:

- с заданным названием;
- с настроенным доменом;
- с назначенной группой;
- с назначенным источником трафика;
- с двумя потоками;
- с корректной логикой распределения посетителей по GEO.

## 9. Критерии готовности

Задача считается выполненной, если:

1. Пользователь может создать кампанию через форму из трёх полей.
2. Кампания действительно появляется в Keitaro.
3. Домен, группа и источник назначены правильно (проверка через `GET /campaigns/{id}`: `domain_id`, `group_id`, `traffic_source_id`).
4. Первый поток отправляет посетителей из выбранной страны на Google.
5. Второй поток отправляет остальных посетителей на выбранный оффер.
6. Оба потока привязаны к созданной кампании.
7. Ошибки API отображаются пользователю, а не скрываются.
8. После создания кампанию можно открыть в интерфейсе Keitaro и проверить её настройки.
9. Кампания, потоки и оффер сохранены в БД, статус кампании `synced`.
10. При сбое созданное в Keitaro удалено, кампания в БД имеет статус `failed` и текст ошибки в `last_error`.

## 10. Эндпойнты нашего бэкенда

Пути совпадают с аналогичными методами Keitaro API (без базового URL). Тело запроса и ответ у наших эндпойнтов свои. Эндпойнт `GET /countries` собственный, аналога в Keitaro нет.

### GET /countries

Список кодов стран ISO 3166-1 alpha-2.

Ответ 200: массив строк, например `["DE", "RU", "US"]`.

### GET /offers

Список офферов Keitaro, полученный через `GET /offers` Keitaro.

Ответ 200: массив объектов `{"id": 123, "name": "Название"}`.

Ошибка Keitaro или недоступность Keitaro: ответ с кодом ошибки и телом из формата ошибок ниже.

### POST /campaigns

Запуск создания кампании (шаги 1-6 раздела 4).

Тело запроса:
- `name` — название кампании;
- `geo` — код страны;
- `offer_id` — ID оффера.

Ответ 200:
- `campaign_id` — ID кампании в Keitaro;
- `name` — название кампании.

### Формат ошибок

Для всех эндпойнтов ошибка возвращается объектом:
- `step` — код шага: `validation`, `campaign`, `stream_google`, `stream_offer`, `db`. Ошибка выбора домена или источника относится к шагу `campaign`;
- `error` — текст ошибки. Для ошибок Keitaro это текст Keitaro без изменений;
- `campaign_id` — ID кампании в Keitaro, если она уже создана, иначе `null`.

Коды ответа: 422 для `validation`, 502 для ошибок Keitaro, 500 для `db`.

Для `GET /countries` и `GET /offers` поле `step` не используется, вместо него `source`: `countries` или `offers`.

## 11. Тесты

Клиент Keitaro в тестах подменяется, реальных запросов к Keitaro нет.

Проверка данных:
- пустое название отклоняется;
- пустая страна, код вне списка `pycountry` и пустой оффер отклоняются;
- запросы к Keitaro при ошибке проверки не отправляются.

Подготовка данных:
- `alias` равен `name` с заменой `_` на `-`;
- `group_id` уходит строкой, `domain_id` и `traffic_source_id` числами;
- домен берётся из списка, если в нём ровно один элемент, иначе ошибка;
- источник трафика: пустой список даёт `traffic_source_id` 0.

Создание потоков:
- тело потока 1: `schema` `redirect`, фильтр `country` с `mode` `accept` и payload из кода страны, `action_options` с URL Google;
- тело потока 2: `schema` `landings`, один оффер с `share` 100;
- в обоих потоках передан `campaign_id` созданной кампании.

Ошибки по шагам (ответ содержит `step` и `error`):
- ошибка создания кампании: потоки не создаются, `campaign_id` null;
- ошибка потока 1: потока 2 нет, в ответе `campaign_id`;
- ошибка потока 2: в ответе `campaign_id`, успеха нет;
- ошибка Keitaro возвращается текстом Keitaro без изменений.

Сохранение в БД:
- при успехе в БД Campaign (статус `synced`), два Stream, Offer и один StreamOffer (`share` 100, `status` active, оба флага false), внешние ID сохранены;
- при сбое на любом шаге созданное в Keitaro удаляется в обратном порядке, кампания получает `failed` и `last_error`, `keitaro_id` обнуляется; если удаление упало, `keitaro_id` остаётся;
- повторное создание кампании с тем же оффером использует существующую запись Offer;
- ошибка записи в БД даёт `step` `db`.

Эндпойнты:
- `GET /countries` возвращает массив кодов;
- `GET /offers` возвращает массив `{id, name}`;
- `POST /campaigns` на успех и на каждый `step` ошибки возвращает схему и код ответа из раздела 10.


# Структура и окружение проекта

## Инициализация окружения

- Проект состоит из двух независимых частей: бэкенд лежит в папке `backend/`, фронтенд в папке `frontend/`. Далее описывается бэкенд, а фронтенд в своём отдельном ТЗ.
- Проект создаётся через uv (`uv init`), пакет `app/` лежит прямо в `backend/`, без `src/`.
- В `pyproject.toml` указать зависимости: fastapi, uvicorn, sqlalchemy (2.0, async), asyncpg, alembic, pydantic-settings, pycountry, httpx.
- Dev-зависимости: pytest, pytest-asyncio, httpx, ruff, mypy.
- Файл requirements.txt не используется, зависимости хранятся только в `pyproject.toml` и `uv.lock`.
- Создать `Dockerfile` (зависимости ставятся через uv) и `docker-compose.yml` с двумя сервисами: app и db (postgres). Контейнер app при старте запускает только uvicorn, миграции автоматически не применяются: после старта их применяют вручную (`docker compose exec app alembic upgrade head`). Команда запуска задана в `docker-compose.yml`, в Dockerfile CMD нет. Код копируется в образ при сборке, после правок образ пересобирается.
- Создать `.env` и `.env.example`. В `.env.example` перечислены все переменные, в `.env` стоят реальные значения. Значения в `.env.example` подобраны так, чтобы приложение запускалось без правок, кроме ключа Keitaro.
- Создать `.gitignore`: `.env`, `.env.*` (кроме `.env.example`), `.venv`, `__pycache__`, `*.pyc`, `.pytest_cache`, `.ruff_cache`, `.mypy_cache`, `.coverage`, `htmlcov`, `dist`, `build`, `.idea`, `.vscode`, `.DS_Store`, `*.log`, локальные тома БД и загрузки (`pgdata`, `uploads`).
- Создать `.dockerignore`: всё из `.gitignore` плюс `.git`, `tests`, `README.md`. Секреты и мусор не попадают в образ.
- Настроить ruff в `pyproject.toml`: длина строки 79, набор правил, целевая версия Python.
- Настройки читаются только из переменных окружения через pydantic-settings, значения в коде не прописываются.
- Добавить проверку работоспособности: эндпойнт `GET /health` и `healthcheck` в compose для сервисов app и db. Сервис app стартует после db: `depends_on` с `condition: service_healthy`.
- Контейнер app запускается не от root.
- Версии образов в Dockerfile и compose указаны явно, без `latest`.

- `api/`: роуты FastAPI (`routes.py`), зависимости (`deps.py`), обработчики исключений (`errors.py`), `GET /health`.
- `core/`: настройки (pydantic-settings), конфигурация логирования, подключение к БД и сессии, клиент Keitaro.
- `models.py`: модели SQLAlchemy.
- `schemas/`: схемы запросов и ответов (pydantic).
- `repositories/`: весь доступ к БД. Роуты и сервисы к БД напрямую не обращаются.
- `services/`: бизнес-логика: создание кампании (`campaign_creator.py`), редактор потоков (`stream_editor.py`), офферы (`offer.py`), исключения сервисов (`exceptions.py`). Сервисы работают с БД только через репозитории, с Keitaro только через клиент Keitaro.
- `main.py`: создание приложения, подключение роутов и обработчиков исключений, настройка логирования. Логирование настраивается в одном месте, уровень берётся из env.
- Зависимости идут в одну сторону: `api` вызывает `services`, `services` вызывают `repositories` и клиент Keitaro. Обратных вызовов нет.

## Репозитории и транзакции

- `repositories/base.py`: класс `BaseRepository` с общими операциями (получить по id, список, добавить, обновить, удалить).
- Конкретные репозитории наследуют `BaseRepository`.
- Транзакция открывается на один сценарий сервиса: при успехе commit, при ошибке rollback. Сами репозитории commit не делают.

## Внедрение зависимостей

- DI-контейнер не используется. Репозитории и сервисы собираются в `api/deps.py` и подключаются в роутах через зависимости FastAPI, напрямую роуты ничего не создают.

## База данных

- Alembic настроен на async-движок, `env.py` берёт URL из настроек.
- В репозитории одна начальная ревизия в `alembic/versions`, созданная через `alembic revision --autogenerate` по итоговым моделям.
- Миграции в автозапуск контейнера не входят, применяются вручную.
- После правок в `alembic/` образ нужно пересобрать.

## Ошибки и логирование

- Ошибки сервисов оформляются собственными классами исключений и переводятся в HTTP-ответы в одном месте, через обработчики исключений FastAPI в `api/`.
- Во всех `try/except` лог пишется в формате, где перед и после сообщения по две пустые строки:

```python
logger.error(
    "\n\n !!! --- ERROR --- !!! %s %s.%s %s e=%s\n\n",
    path,
    cls_name,
    method_name,
    what_failed,
    e,
)
```

  Здесь `path` это полный путь к файлу, `cls_name` класс, `method_name` метод, `what_failed` что именно не удалось.

## Тесты и проверки

- Интеграционные тесты репозиториев на реальной БД из compose.
- `ruff check` и `ruff format` запускаются после каждой правки.

# Редактор потоков (вне исходного ТЗ создателя)

Бэкенд редактора: сервис `StreamEditor` и схемы `AddOfferRequest`,
`PinRequest`, `StreamOfferOut`, `StreamOut`, `CampaignOut`
(`app/schemas/editor.py`). Операции сервиса:

- `fetch`: потоки кампании из Keitaro и клики за сегодня
  (`POST /report/build`) в БД; оффера, удалённые в Keitaro, становятся
  серыми (`removed`);
- `view_campaign`: чтение кампании из БД;
- `add_offer`, `remove_offer`, `bring_back`, `set_pin`: правки только
  в БД, веса пересчитываются поровну, закреплённый вес не меняется;
- `push`: запись офферов потока в Keitaro (`PUT /streams/{id}`),
  сумма долей должна быть 100;
- `cancel`: перечитывает потоки Keitaro и возвращает привязки к
  состоянию Keitaro; для потока без ID в Keitaro возвращает ошибку.

Поиск кампании редактором по `keitaro_id`
(`CampaignRepository.get_by_keitaro_id`) возвращает только кампании
со статусом `synced`.

Эндпойнты редактора в этом файле не описаны, их пути смотреть в
`app/api/`.
